# Task 5: incident photographs and repair evidence

## Recovery from Copilot

Work began from the existing uncommitted changes on `develop`, following commit `d896ed8`. No changes were staged. The existing `IncidentAttachment` entity, attachment migration, storage client, scoped resident-upload capability, attachment controller/service, resident previews and retry screen, staff evidence component and evidence styling were retained and completed. Nothing was reset, stashed or replaced with a separate implementation.

The recovered implementation was missing tests and verified storage setup. Its photo-count check could race, retries could duplicate photos, some formats were rewritten, and the resident form remained busy after a failed upload. Supabase also returned a missing bucket as HTTP 400 with `NoSuchBucket`, which the original bucket-creation code did not handle.

## Completed behaviour

- The private Supabase bucket is `incident-evidence`, restricted to JPEG, PNG and WebP with a 5 MiB file-size limit. The backend creates it privately when absent and refuses an existing public bucket. Storage requests do not follow redirects.
- PostgreSQL `IncidentAttachments` metadata links every photo to an incident, its category, uploader, original name, content type, size, original-byte SHA-256 and creation time. Table RLS and revoked anonymous/authenticated grants preserve backend-only access.
- A report that requests photo uploads receives a two-hour HMAC-signed capability in an HttpOnly cookie scoped to that incident's upload route. The upload also requires an explicitly allowed origin. Outside Development, photo capability issuance and upload require HTTPS. Knowing an incident ID alone grants no upload or retrieval permission.
- Resident file selection and camera capture share the three-photo limit and local previews. The saved report is retained when uploads fail. Retrying reuses the photo identity, does not create another incident and does not consume another slot for an already-saved photo. Residents can proceed to confirmation if remaining photos cannot be uploaded.
- Staff can view report photos and upload repair evidence through the existing staff policy. Image bytes are fetched through the backend, never through a public storage URL. Copilot's limit of three photos per category is retained.
- PostgreSQL row locks serialize the attachment count and metadata write per incident. Storage cleanup compensates for a failed metadata write; cleanup failures are logged for operational follow-up.
- Original image bytes are retained, including any original metadata, in private storage. Retrieval verifies the saved hash and uses explicit image content types, `nosniff`, CSP sandbox and private/no-store caching. No image conversion to percentages, telemetry changes or new detection claims are involved.

## Configuration

Save these server-only Windows user environment variables; never place them in React's `.env` or commit their values:

- `Storage__SupabaseUrl`: the HTTPS Supabase project URL.
- `Storage__ServiceRoleKey`: the server secret key or legacy service-role key, never the public anon/publishable key.
- `Storage__UploadCapabilityKey`: generated by `scripts/Initialize-Storage.ps1` if not already saved.

Run `pwsh -File scripts/Initialize-Storage.ps1`, then restart the API so it imports the saved settings. `scripts/Start-Api.ps1` now loads these settings alongside the existing database and telemetry settings. Use the same hostname for local Vite and API URLs, for example localhost on both, so the scoped cookie is same-site.

The API supports newer Supabase secret keys using the `apikey` header, and legacy service-role JWTs with both `apikey` and Bearer headers. Keys and upload capabilities are not returned in attachment metadata.

## Endpoints

- `POST /api/incidents` with `requestPhotoUploadCapability: true` creates the report and issues the cookie. A normal report without photos retains its existing contract.
- `POST /api/public/incidents/{id}/attachments`: multipart `photo`, optional stable `uploadId`, scoped capability cookie and allowed Origin required.
- `GET /api/incidents/{id}/attachments`: staff-only metadata list.
- `GET /api/incidents/{id}/attachments/{attachmentId}/content`: staff-only image streaming after incident/attachment lookup and hash verification.
- `POST /api/incidents/{id}/attachments`: staff-only multipart repair photo, with an optional stable `uploadId` for retries.
